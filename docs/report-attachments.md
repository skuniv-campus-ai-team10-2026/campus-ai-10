# 신고 사진 첨부 — 파일 정리와 운영 메모

기준일: 2026-10-23. 브랜치 `feature/report-attachments` (PR #1). API 명세·오류 코드·화면 연결 방법은 PR #1 본문을 따른다. 이 문서는 사진 파일과 DB 기록이 어긋나지 않게 하는 정리 장부(V6)와 그 한계를 설명한다.

## 왜 정리 장부가 필요한가

사진은 DB(`report_attachments`)와 디스크 파일 두 곳에 나뉘어 저장된다. 둘을 한 트랜잭션으로 묶을 수 없으므로, 한쪽만 성공하면 "DB 기록 없는 파일"이 남을 수 있다. 처음 구현에서는 삭제 후 파일 정리가 실패하면 DB 기록은 이미 지워져 그 파일을 다시 찾을 수 없었다(PR #1 리뷰 지적).

`attachment_cleanup`(V6)은 "정리가 필요할 수 있는 파일" 목록이다. **파일 작업보다 먼저 기록이 커밋되고, 파일이 사라진 것이 확인된 뒤에만 지워진다.**

| 흐름 | 순서 |
|---|---|
| 업로드 | ① 장부 기록 커밋(별도 트랜잭션) → ② 파일 쓰기 → ③ 한 트랜잭션: 신고 잠금·재확인 + 첨부 INSERT + 장부 삭제 → 커밋. ②③ 실패 시 즉시 파일 삭제를 시도하고, 그것도 실패하면 장부에 남는다. 서버가 어느 단계에서 멈춰도 ① 이후라면 장부가 남는다. |
| 삭제 | ① 한 트랜잭션: 첨부 행 삭제 + `ATTACHMENT_DELETED` 이력 + 장부 기록 → 커밋 → ② 파일 삭제 → 성공하면 장부 삭제, 실패하면 장부에 남김(시도 횟수·오류·시각 기록). 학생 응답은 204다. 사진은 ①에서 이미 누구도 볼 수 없다. |

파일 삭제 결과는 세 가지로 구분한다. `DELETED`(지움)와 `ALREADY_GONE`(원래 없음)은 정리 완료, `FAILED`만 재시도 대상이다.

## 정상 파일과 진행 중 업로드 보호

재시도는 장부 행을 `FOR UPDATE`로 잠근 뒤 아래 순서로 판단한다.

1. 키를 `report_attachments`가 참조하면 정상 사진이다. 파일은 두고 장부 행만 지운다.
2. 이 서버가 지금 업로드 중인 키(메모리의 in-flight 목록)면 건너뛴다. **시간과 관계없이** 보호된다.
3. 다른 서버 인스턴스(재시작 전 서버 포함)가 만든 행은 10분이 지난 뒤에만 처리한다. 다른 인스턴스의 in-flight 목록은 볼 수 없기 때문이다.
4. 그래도 다른 인스턴스가 진행 중인 업로드의 장부를 가져가면, 그 업로드는 마지막 단계(첨부 INSERT와 장부 삭제를 함께 커밋)에서 장부 행이 없어 503으로 실패한다. "첨부 행은 있는데 파일이 없는" 상태는 생기지 않는다.

## 재시도 시점과 처리량

- 서버 시작 시(`ApplicationReadyEvent`) 1회
- 학생의 사진 업로드·삭제 요청이 끝날 때마다 1회
- 한 번에 최대 20건, 오래된 순서. 실패한 항목은 1분이 지나야 다시 시도한다.
- 공통 설정(`@EnableScheduling`)은 바꾸지 않아 주기 실행은 없다.

## 알려진 제한과 재처리 방법

**시작 시 10분이 지나지 않은 항목은 남을 수 있다.** 재시작 직전에 생긴 항목은 3번 규칙 때문에 시작 시 처리되지 않는다. 이후 첨부 업로드·삭제가 없으면 다음 재시작까지 남는다. 장부에 남아 있으므로 파일을 잃어버리지는 않는다. 다음 중 하나로 처리된다.

1. 10분이 지난 뒤 아무 학생이 사진을 업로드하거나 삭제한다.
2. 10분이 지난 뒤 서버를 다시 시작한다.

남은 항목 확인(MySQL):

```sql
SELECT storage_key, reason, attempts, last_error, created_at, last_attempt_at
FROM attachment_cleanup ORDER BY created_at;
```

`attempts`가 계속 늘어나면 파일이 다른 프로그램(백신, 사진 뷰어, 동기화 도구)에 잡혀 있거나 폴더 권한 문제일 가능성이 크다. 원인을 해결하면 다음 재시도에서 정리된다. 장부 행을 손으로 지우면 추적이 끊기므로, 파일을 직접 지운 경우에만 지운다(이미 없는 파일은 다음 재시도에서 자동으로 정리 완료 처리된다).

그 밖의 제한:

- 다중 서버 배포에서는 3번 규칙(10분)이 다른 서버의 진행 중 업로드 보호를 맡는다. 10분 넘게 걸리는 업로드는 실패할 수 있다(파일·DB 불일치는 생기지 않음).
- 장부 기록 자체(업로드 ①)가 실패하면 파일을 쓰지 않고 503을 반환한다.
- 쓰다 만 `.part` 파일은 장부와 별개로 서버 시작 시 삭제된다.

## 강제 종료 복구: 확인한 범위와 확인하지 못한 범위

**확인함**
- 자동 테스트(H2·MySQL): 삭제 후 파일 정리 실패 → 장부 기록 → 재시도 정리, 업로드 DB 실패 + 정리 실패 → 장부 기록 → 재시도 정리, 정상 파일 보존, 진행 중 업로드 보호(장부 시각을 30분 전으로 조작해도 보호), 다른 인스턴스의 경합 시 깔끔한 실패, 20건 처리 제한, 이미 없는 파일 처리, Windows 파일 잠금으로 만든 실제 삭제 실패(`FAILED`)
- 자동 테스트의 "재시작"은 새 인스턴스 ID를 가진 `AttachmentCleanup` 객체로 모의했다.
- **실제 프로세스 재시작 (2026-10-23, 로컬 MySQL 8.0.45)**: bootJar 서버 실행 → 장부 행 + 파일 2개(30분 전, 2분 전)를 만든 상태에서 `Stop-Process -Force`로 강제 종료 → 재시작. 30분 된 파일과 장부는 삭제되고(`Attachment cleanup at startup removed 1 leftover file(s)`), 2분 된 파일과 장부는 남았다.

**확인하지 못함**
- 실제 업로드 요청 처리 중 정확히 특정 단계(장부 커밋 직후, 파일 쓰기 도중, 첨부 커밋 직전)에서 프로세스를 죽이는 실험. 위 실험은 그 상황이 남기는 DB·파일 상태를 직접 만들어 재시작만 실제로 확인했다.
- 트랜잭션 도중 DB 연결 끊김, 디스크 가득 참, 서버 여러 대 동시 운영
- 실제 휴대폰 사진, 브라우저 화면 연결 후 통합 흐름(PR #1 미검증 항목 그대로)
