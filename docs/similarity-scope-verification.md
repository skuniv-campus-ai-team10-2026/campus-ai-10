# 유사 신고 범위·Embedding 검증 및 전환 절차

검증일: 2026-10-31. 기준 main `3d86b20`. 구현·로컬 검증 완료, Azure 반영 전입니다.

## 결정한 변경

- 기본 기준 0.82 / 기존 WiFi 보조 기준 0.70 / 같은 건물 / 기존 유형·대상·기간·권한 조건은 유지합니다. 후보는 관리자가 확정하며 자동 사건 연결은 하지 않습니다.
- Embedding 입력은 기존 `분류 | 장소 | 증상 | 원문`을 유지합니다. 실제 비교 결과가 더 나았던 `text-embedding-3-large`를 권장합니다. LLM·프롬프트·배정·신고 저장 계약은 바꾸지 않습니다.
- 같은 층의 공통 무선망 신고는 실제 비교 가능한 벡터가 있고 접수 간격이 24시간 이내이면 다른 호실도 후보 검색에 포함합니다. 서로 다른 망인지 확인된 것은 아니므로 후보 설명에 범위 미확정 사실을 표시합니다.
- 양쪽 신고의 원문과 최종 증상에 모두 건물 전체 장애가 명시되면 층·호실 경계를 넓힙니다. 층·구역 전체 장애는 양쪽에 같은 층이 확인된 경우에만 넓힙니다. 두 발생일이 모두 알려져 있고 다르면 확장하지 않습니다.
- 개별 시설은 남녀 화장실, 첫째/둘째 칸, 창가/출입문, 좌우·방향처럼 명시적으로 다른 지점을 구분합니다. 화장실 이름만 같다는 이유로 서로 다른 변기를 묶지 않습니다. 실제 입력 장소는 변경하지 않습니다.
- 규칙 전용·벡터 실패·건물 미확인 상황에서는 범위 확장을 하지 않습니다. 물건마다 새 유형이나 질문을 추가하지 않았습니다.

## 실제 벡터 비교 결과

각 표본은 서로 다른 신고 2건씩으로 구성했습니다. 정답은 호출 전에 고정했습니다. TP=같은 문제 탐지, FP=다른 문제 오탐, TN=다른 문제 제외, FN=같은 문제 누락입니다.

| 표본 | 변경 전: small + 기존 장소 정책 (TP/FP/TN/FN) | 변경 전 Precision / Recall | 변경 후: large + 새 장소 정책 (TP/FP/TN/FN) | 변경 후 Precision / Recall |
|---|---|---|---|---|
| DEV: 기존 개발 회귀 16쌍 | 4/0/8/4 | 100% / 50% | 8/0/8/0 | 100% / 100% |
| NEW: 새 개발·선정 표본 16쌍 | 4/5/3/4 | 44.44% / 50% | 7/0/8/1 | 100% / 87.5% |
| HOLDOUT: 구현 고정 후 새 표본 8쌍 | 1/2/2/3 | 33.33% / 25% | 3/0/4/1 | 100% / 75% |

DEV와 NEW는 변경·모델 선정에 사용한 개발 결과입니다. HOLDOUT은 제품 코드 3개 파일의 해시를 고정한 뒤 만들었고 결과에 맞춰 구현을 바꾸지 않았습니다. **모든 정답은 Codex가 작성한 합성 정답이며 사람의 독립 검수나 실제 사용자 정확도가 아닙니다.** 세 표본을 합쳐 독립 정확도로 발표하지 않습니다.

실제 OpenAI 벡터를 저장한 뒤 현재 `SimilarityService.index`와 분리 H2 DB로 후보 생성까지 재생했습니다. DEV/NEW의 변경 전은 기존 코드 실행 결과와 대조했습니다. HOLDOUT의 변경 전은 저장 점수에 기존 장소 정책을 적용한 반사실 계산이며, 과거 배포 서버에서 직접 실행한 결과는 아닙니다. 상세 점수·제외 이유는 [결과 JSON](evaluation/similarity-scope-v1-results.json)에 있습니다. JUnit 실행 성공과 품질 사례 PASS는 구분하며 FAIL도 그대로 기록합니다.

### 모델과 입력 형식을 함께 비교한 이유

- 새 장소 정책만 적용하고 small을 유지하면 DEV Recall 50%, NEW 75%, HOLDOUT 25%였습니다. 기존 누락을 해결하기에는 부족했습니다.
- 장소를 뺀 의미 요약만 Embedding하면 같은 0.82에서 DEV/NEW Recall이 각각 12.5%였습니다. 관찰 원문 일부를 추가해도 25%/12.5%여서 채택하지 않았습니다. 입력을 바꾼 뒤 같은 임계값을 최적이라고 일반화할 수는 없습니다.
- large만 바꾸고 기존 장소 정책을 유지하면 DEV FP 1, NEW FP 5가 생깁니다. 모델 교체만으로 해결됐다고 설명하면 안 됩니다.
- 벡터마다 모델명을 보존하고 모델·차원이 다른 벡터는 직접 코사인 비교하지 않습니다. 임계값을 이 표본에 맞춰 낮추지 않았습니다.

### 남은 누락과 한계

- NEW N02: 건물 전체 무선망 장애의 다른 층 신고. large 코사인 **0.8171667 < 0.82**로 누락입니다. 0.003 차이만 보고 기준을 낮추지 않았습니다.
- HOLDOUT H04: 같은 프로젝터를 `프로젝터`/`빔프로젝터`로 표현. 코사인 **0.940884**이지만 기존 `WORK_GROUP_TARGET`의 명칭 근거 조건에서 제외됩니다. 물건별 예외를 추가하지 않았습니다. 후속 개선 시 이 사례는 개발 표본으로 옮기고 별도 새 평가가 필요합니다.
- 공통 장애 범위가 최초 원문에는 없고 추가 답변에만 있는 경우에는 현재 보수적인 원문 근거 검사 때문에 범위가 넓어지지 않을 수 있습니다.
- 구체 위치나 장애 범위가 LLM의 최종 장소·증상에서 빠지면 해당 구분을 활용하지 못합니다. 이번 작업은 Embedding·후보 정책 평가이며 실제 LLM 추출 빈도는 측정하지 않았습니다.
- 표현 목록 밖의 위치·부정 표현, 지점이 여러 개 섞인 문장, 실제 복합 장애 전체를 해결했다고 주장하지 않습니다. 후보는 관리자가 최종 판단합니다.

## 검증 범위와 비용

| 검증 | 결과 |
|---|---|
| 전체 백엔드 H2 | 588건 중 572 PASS, 16 SKIP, FAIL/ERROR 0 |
| 전체 백엔드 MySQL 8.0.45 | 588건 중 572 PASS, 16 SKIP, FAIL/ERROR 0 |
| 이후 추가한 실제 HTTP 연동 3건 | H2 3 PASS, MySQL 3 PASS; 세션·CSRF·신고 저장·후보·권한·관리자 결정 보존 확인 |
| 유지보수 실행 생명주기 | 분리 H2 + 가짜 공급자: 지정 2건 벡터 갱신, 장부 2회, 후보 1쌍, 자동 사건 0, 작업 종료 확인 |
| 실제 OpenAI Embedding | 256개 새 벡터, HTTP 요청 16회, 실패·자동 재시도 0; 이전 32개 벡터 재사용 |
| LLM·배포 서버·브라우저 | 이번 변경의 새 LLM 호출 0; 배포 서버·브라우저 직접 검증 미실행; UI 변경 없음 |

총 입력 **16,595 토큰**, 추정 비용 **$0.00107121**, 사전 총 비용 상한 **$0.02** 안에서 종료했습니다. small 10요청/160벡터/8,579토큰/$0.00017158, large 4요청/64벡터/5,426토큰/$0.00070538, holdout 2요청/32벡터/2,590토큰/$0.00019425입니다. 배치 한 요청이 여러 벡터를 만드므로 벡터 수와 HTTP 호출 수가 다릅니다. 이 로컬 평가 비용은 Azure 앱 장부에 포함되지 않으며 공급자 청구 확정액도 아닙니다.

가격 근거: [small 공식 모델 문서](https://developers.openai.com/api/docs/models/text-embedding-3-small), [large 공식 모델 문서](https://developers.openai.com/api/docs/models/text-embedding-3-large). 이번 추정은 입력 100만 토큰당 각각 $0.02 / $0.13을 사용했습니다. 프런트는 변경하지 않아 기존 102개 테스트·빌드 결과를 재사용했습니다.

## 병합 후 서버 전환

현재 서버·키·사용량 장부는 바꾸지 않았습니다. `.env.example`은 권장값만 표시하며 자동 로드되지 않습니다. DB 마이그레이션·공개 API·UI 변경은 없습니다.

1. 배포 담당자가 병합 커밋·실제 JAR 경로·환경변수 로드 방법을 확인합니다. DB·사진·환경설정 백업과 서버 밖 사본을 확보합니다. API 키를 명령행·메신저·로그에 넣지 않습니다.
2. 현재 사용량과 남은 Embedding 한도를 확인합니다. 대상 건수만큼 호출할 수 있어야 하며 부족하면 기록을 지우지 말고 합의한 한도만 조정합니다. 재색인 대상은 내부 DB에서 다음 조회로 확정합니다. 문의나 검토 메모가 있는 신고는 대상에서 제외합니다.

   ```sql
   SELECT id FROM reports
   WHERE request_kind='REPORT' AND review_note IS NULL ORDER BY id;
   ```

3. 짧은 점검 시간에 주 서비스 쓰기를 중지하고, **배포할 새 JAR**에 기존 서버 환경변수를 안전하게 전달한 상태로 아래 일회성 작업을 실행합니다. `SKOPE_JAR`는 담당자가 확인한 실제 파일 경로이며 임의 경로를 사용하지 않습니다. ID·상한은 실제 대상에 맞춥니다.

   ```sh
   java -jar "$SKOPE_JAR" \
     --server.address=127.0.0.1 --server.port=0 \
     --EMBEDDING_MODE=LIVE \
     --EMBEDDING_MODEL=text-embedding-3-large \
     --EMBEDDING_PRICE_PER_MTOK=0.13 \
     --skope.similarity.reindex.enabled=true \
     --skope.similarity.reindex.ids=<쉼표로_구분한_실제_ID> \
     --skope.similarity.reindex.max-reports=<실제_작업_상한>
   ```

4. 명시 ID·중복·자격·1~100건 상한을 첫 호출 전에 검사합니다. 기본 상한 20건입니다. 기존 AI 비용 장부를 사용하고 실패 시 자동 재시도 없이 중단합니다. 먼저 선택한 벡터를 모두 채운 뒤 후보를 재계산하므로 모델 혼재 상태로 후보를 계산하지 않습니다. 한 번 성공한 같은 모델 벡터는 재사용합니다. 관리자 확정·거절 결정은 보존합니다.
5. 완료 문구·실제 저장 모델·차원·사용량·후보·관리자 결정 보존을 확인합니다. 상시 설정에 `EMBEDDING_MODEL=text-embedding-3-large`, `EMBEDDING_PRICE_PER_MTOK=0.13`을 함께 적용하고 새 버전 서비스를 시작합니다. **일회성 reindex 설정을 상시 서비스에 넣지 않습니다.** LLM 모델은 그대로 둡니다.
6. HTTPS·권한·후보·학생 결과를 최소 점검하고 배포 커밋과 결과를 공유합니다. 실패 시 부분 갱신이 있을 수 있으므로 모델 설정만 되돌리지 말고 백업과 실제 벡터 상태를 함께 확인합니다.

기존 small 벡터를 그대로 둔 채 large로 바꾸면 모델 혼재 쌍은 기존 정책상 RULE_ONLY로 폴백합니다. 평가에서 본 효과를 서버에 적용하려면 대상 벡터 전환까지 완료해야 합니다. 운영 작업은 아직 실행하지 않았습니다.

## 비용 없는 재생

저장된 벡터 증거 묶음의 manifest와 cache를 지정합니다. API 키 없이 실행하며 누락 캐시는 실패로 처리합니다. 새 결과 폴더를 사용해야 하며 기존 결과를 덮어쓰지 않습니다.

```powershell
$env:SKOPE_SIMILARITY_SCOPE_EVAL='1'
$env:SKOPE_SCOPE_MANIFEST='<증거 폴더>\scope-all-manifest.json'
$env:SKOPE_SCOPE_CACHE='<증거 폴더>\cache'
$env:SKOPE_SCOPE_OUTPUT='<새 결과 폴더>'
.\backend\gradlew.bat -p backend cleanTest test --tests edu.skope.service.SimilarityScopeEvaluationTest --console=plain
```

고정 정답은 `similarity-review-v2.json`, `similarity-scope-v1.json`, `similarity-scope-holdout-v1.json`이며 실행기가 해시를 검사합니다. HOLDOUT은 제품 코드 해시도 검사하므로 이후 변경 뒤에는 새 평가로 오인하지 않도록 별도 개발 재생 절차가 필요합니다.
